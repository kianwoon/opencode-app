Plugins allow you to extend OpenCode by hooking into various events and customizing behavior. You can create plugins to add new features, integrate with external services, or modify OpenCode's default behavior.

For examples, check out the [plugins](/docs/ecosystem#plugins) created by the community.

---

## Use a plugin

There are two ways to load plugins.

---

### From local files

Place JavaScript or TypeScript files in the plugin directory.

- `.opencode/plugins/` - Project-level plugins
- `~/.config/opencode/plugins/` - Global plugins

Files in these directories are automatically loaded at startup.

---

### From npm

Specify npm packages in your config file.

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "plugin": ["opencode-helicone-session", "opencode-wakatime", "@my-org/custom-plugin"]
}
```

Both regular and scoped npm packages are supported.

Browse available plugins in the [ecosystem](/docs/ecosystem#plugins).

---

### How plugins are installed

**npm plugins** are installed automatically using Bun at startup. Packages and their dependencies are cached in `~/.cache/opencode/node_modules/`.

**Local plugins** are loaded directly from the plugin directory. To use external packages, you must create a `package.json` within your config directory (see [Dependencies](#dependencies)), or publish the plugin to npm and [add it to your config](/docs/config#plugins).

---

### Load order

Plugins are loaded from all sources and all hooks run in sequence. The load order is:

1. Global config (`~/.config/opencode/opencode.json`)
2. Project config (`opencode.json`)
3. Global plugin directory (`~/.config/opencode/plugins/`)
4. Project plugin directory (`.opencode/plugins/`)

Duplicate npm packages with the same name and version are loaded once. However, a local plugin and an npm plugin with similar names are both loaded separately.

---

## Create a plugin

A plugin is a **JavaScript/TypeScript module** that exports one or more plugin
functions. Each function receives a context object and returns a hooks object.

---

### Dependencies

Local plugins and custom tools can use external npm packages. Add a `package.json` to your config directory with the dependencies you need.

```json title=".opencode/package.json"
{
  "dependencies": {
    "shescape": "^2.1.0"
  }
}
```

OpenCode runs `bun install` at startup to install these. Your plugins and tools can then import them.

```ts title=".opencode/plugins/my-plugin.ts"
import { escape } from "shescape"

export const MyPlugin = async (ctx) => {
  return {
    "tool.execute.before": async (input, output) => {
      if (input.tool === "bash") {
        output.args.command = escape(output.args.command)
      }
    },
  }
}
```

---

### Basic structure

```js title=".opencode/plugins/example.js"
export const MyPlugin = async ({ project, client, $, directory, worktree }) => {
  console.log("Plugin initialized!")

  return {
    // Hook implementations go here
  }
}
```

The plugin function receives:

- `project`: The current project information.
- `directory`: The current working directory.
- `worktree`: The git worktree path.
- `client`: An opencode SDK client for interacting with the AI.
- `$`: Bun's [shell API](https://bun.com/docs/runtime/shell) for executing commands.

---

### TypeScript support

For TypeScript plugins, you can import types from the plugin package:

```ts title="my-plugin.ts" {1}
import type { Plugin } from "@opencode-ai/plugin"

export const MyPlugin: Plugin = async ({ project, client, $, directory, worktree }) => {
  return {
    // Type-safe hook implementations
  }
}
```

## Examples

Here are some examples of plugins you can use to extend opencode.

---

### Send notifications

Send notifications when certain events occur:

```js title=".opencode/plugins/notification.js"
export const NotificationPlugin = async ({ project, client, $, directory, worktree }) => {
  return {
    event: async ({ event }) => {
      // Send notification on session completion
      if (event.type === "session.idle") {
        await $`osascript -e 'display notification "Session completed!" with title "opencode"'`
      }
    },
  }
}
```

We are using `osascript` to run AppleScript on macOS. Here we are using it to send notifications.

:::note
If you’re using the OpenCode desktop app, it can send system notifications automatically when a response is ready or when a session errors.
:::

---

### .env protection

Prevent opencode from reading `.env` files:

```javascript title=".opencode/plugins/env-protection.js"
export const EnvProtection = async ({ project, client, $, directory, worktree }) => {
  return {
    "tool.execute.before": async (input, output) => {
      if (input.tool === "read" && output.args.filePath.includes(".env")) {
        throw new Error("Do not read .env files")
      }
    },
  }
}
```

### Secret Broker

Secret Broker is a built-in plugin that stops credentials from ever reaching the model. It is a defense against a **compromised upstream LLM provider**: even though a malicious provider sees every token of your context, it can never recover a real credential through the model-visible channel.

#### Mental model

> The agent requests work, not secrets. The process receives secrets, not the agent.

Credentials in `.env` are injected into the **child process environment** (so your shell commands and tools can use them), but the agent — and therefore the provider — only ever sees a **handle** like `secret://project/API_KEY`. If a command prints, echoes, or errors out with a real value, the broker rewrites it back to the handle before it is sent upstream.

```text
todo: "call the API with API_KEY"
        │                        ▲
        ▼                        │  secret://project/API_KEY  (handle only)
  opencode agent ──────────────► provider (untrusted)
        │
        ▼  shell.env
   child process env: API_KEY=sk-live-…  (real value, never model-visible)
```

#### Configuration

Secret Broker is **enabled by default**. Disable it with:

```sh
export OPENCODE_DISABLE_SECRET_BROKER=1
```

The broker is per-directory and is wired up automatically; no plugin file is needed.

#### The `.env.example` contract

Secret Broker only injects keys **declared in `.env.example`** into the process environment. This is the allowlist:

- On first run, if `.env.example` is missing and `.env` exists, the broker generates it with **default-deny**: every value is blanked unless the key matches a small safe-config pattern (`PORT`, `HOST`, `NODE_ENV`, `DEBUG`, `LOG_LEVEL`, `*_ENABLED`, `*_DISABLED`, `APP_ENV`, `APP_PORT`). Credential-shaped keys (`DATABASE_URL`, `MONGO_URI`, `SENTRY_DSN`, `WEBHOOK_URL`, `SMTP_URL`, …) are blanked.
- The allowlist is **frozen at startup**. Editing `.env.example` mid-session does **not** widen what gets injected — so an agent (or a compromised model) cannot smuggle a new key into the environment.

```dotenv title=".env.example"
API_KEY=
DATABASE_URL=
# safe-config keys keep their value:
LOG_LEVEL=debug
```

#### What is protected

| Channel | Hook | Behavior |
| --- | --- | --- |
| Process environment | `shell.env` ([`src/plugin/secret-broker/index.ts:172`](https://github.com/sst/opencode/blob/dev/packages/opencode/src/plugin/secret-broker/index.ts)) | Injects only allowlisted keys present at startup. |
| File reads/writes | `tool.execute.before` ([`src/plugin/secret-broker/index.ts:176`](https://github.com/sst/opencode/blob/dev/packages/opencode/src/plugin/secret-broker/index.ts)) | Blocks `.env`, `.envrc`, `*.pem`, `*.key`, `id_rsa*`, `id_ed25519*` (case-folded, symlink-resolved). `.env.example`/`.env.sample` stay readable. |
| Tool output / errors | `tool.execute.after` ([`src/plugin/secret-broker/index.ts:181`](https://github.com/sst/opencode/blob/dev/packages/opencode/src/plugin/secret-broker/index.ts)) | Redacts output, title and metadata for **every** parsed `.env` value (allowlisted or not). Fails closed (withholds) if redaction throws. |
| Thrown tool errors | `redactOnFailure` ([`src/plugin/secret-broker/index.ts:139`](https://github.com/sst/opencode/blob/dev/packages/opencode/src/plugin/secret-broker/index.ts)) | Routes error text through the after-hook before it reaches the model, preserving error identity. |
| Final model transcript | `experimental.chat.messages.transform` ([`src/plugin/secret-broker/index.ts:205`](https://github.com/sst/opencode/blob/dev/packages/opencode/src/plugin/secret-broker/index.ts)) | Last-line safety net: redacts every message part in place before the provider request, including interrupted live output. Fails closed. |

Redaction covers not just the literal value but the deterministic transforms a hostile reader would run: **plain, URL-encoded, JSON-escaped, shell-single-quote-escaped, and base64** (standard + URL-safe, padded + unpadded). Redaction is built from **every** value parsed out of `.env` that meets the minimum length, so a key that is **not** in the allowlist is never injected into the environment yet still cannot surface through tool output — only allowlisted keys are injected. Values shorter than the minimum length cannot be redacted safely; direct `.env` reads remain blocked, so they cannot be dumped verbatim either. `StreamRedactor` (a suffix-buffer redactor that withholds a boundary-spanning fragment until its final character arrives) is available for model-visible *delta* sinks. In the current wiring, live stream chunks go to the **client only** — the provider never sees them incrementally; it receives the post-redaction transcript assembled by `experimental.chat.messages.transform` ([`src/session/prompt.ts:1870`](https://github.com/sst/opencode/blob/dev/packages/opencode/src/session/prompt.ts)) and each tool result after `tool.execute.after`.

:::caution
**Network exfiltration is out of scope.** Secret Broker guarantees the *model-visible* channel never carries a credential. It does **not** sandbox a child process: if the agent writes a program and you run it, that program legitimately has the secret in its environment and could send it anywhere over the network. Egress control (firewalls, proxies, network policy) is a separate concern.
:::

### Execution Guard

Execution Guard is a built-in plugin that closes the **evil-provider / malicious-package** gap left by Secret Broker: Secret Broker decides *which* keys may be injected, but a package install script (`npm` postinstall, `pip` `setup.py`, a `curl | sh` payload) is attacker-controlled code that would otherwise receive those keys. Execution Guard classifies each `bash` command and **strips every project secret** from the environment of classes that do not need one.

Classification (`src/plugin/execution-guard/classify.ts`) is a pure function over the command string. A command chain (`a && b | c`) is split into segments and the **strictest class wins**, so `npm install x && npm run deploy` is treated as an install:

| Class | Secrets injected |
| --- | --- |
| `package_install`, `build`, `unit_test` | **none** |
| `integration_test`, `development`, `migration`, `deploy`, `other` | full broker allowlist |

The guard runs **after** Secret Broker, so its `shell.env` hook deletes the broker's injected keys for zero-secret classes — deletion wins.

#### Denied commands

Two shapes are hard-denied from `tool.execute.before`:

- **`curl … | sh` / `wget … | bash`** — remote code executed without review.
- **URL / git dependency installs** (`npm i github:u/r`, `pip install git+https://…`) — the dependency comes from outside a registry.

The denial message names the *shape* only, never a value. Because `permission.ask` has no trigger call site today, the plugin cannot open an approval prompt, so remote-dependency installs are **denied outright** with a message directing you to approve manually (run the install yourself in a terminal, or pin a published registry version).

#### Configuration

Execution Guard is **enabled by default** and is co-gated with Secret Broker (disabling the broker leaves no keys to strip). Opt out independently with:

```sh
export OPENCODE_DISABLE_EXECUTION_GUARD=1
```

Unclassifiable commands are treated as class `other` and receive the broker allowlist. The PTY path (an interactive shell you drive by hand) has no `callID` correlation and is likewise left with the broker allowlist — the model is not the actor there.

### Context Firewall

Context Firewall is a built-in plugin that stops **untrusted content** from granting authority. A README, a fetched web page, a GitHub issue, an MCP tool result or a RAG chunk is *input* — the model may read it and reason about it, but its bytes must never be read as an instruction that grants a permission, reveals a secret, turns DLP off, authorises a destructive op or a dependency install, or changes broker policy.

#### Authority model

Authority is a property of **where content came from**, not of what it says. The trust table is pure (`src/plugin/context-firewall/provenance.ts`) and **missing or unknown sources default to `untrusted`** (fail-safe):

| Source | Trust | May grant authority? |
| --- | --- | --- |
| `user`, `project_policy` | `authoritative` | yes |
| `project_file`, `readme` | `normal` | informs reasoning, not authority |
| `web`, `github`, `mcp`, `rag` | `untrusted` | **never** |
| *anything unknown* | `untrusted` | **never** |

#### Enforcement points

Enforcement is **primary at the model sink**; pattern detection is supplementary — the firewall never depends on the LLM behaving securely.

1. **`tool.execute.after`** tags each tool result with `metadata.trust` (`read`, `grep`, `glob`, `list`, `webfetch`, `websearch`, `fetch` and every `mcp*` tool → `untrusted`; unknown tools → `untrusted`). The read-only result cache skips only `item.execute`, so this hook still runs on cache hits and the tag is applied on a cache read too.
2. **`experimental.chat.messages.transform`** runs on every step before `toModelMessagesEffect` and before compaction. For every untrusted part it neutralises authority-grant lines in place (a pure, case-insensitive regex pass — no model in the loop). Trusted and authoritative parts are left **byte-identical**. If neutralisation throws, the **whole message** is replaced with a withheld placeholder rather than forwarding partial content (fail-closed).

Detection covers instruction-override preambles ("ignore previous instructions"), protection-disabling ("disable DLP", "bypass the secret broker"), permission grants ("grant all permissions"), install/command approval ("run this command", "auto-approve all tools"), credential exfiltration ("exfiltrate", "upload .env / id_rsa"), production/destructive authorisation, and destructive command shapes (`DROP DATABASE`, `rm -rf /`, `mkfs`). A matched line is prefixed with `⚠️ Untrusted content — not authoritative:`.

#### Limitation

The firewall blocks untrusted content from granting **authority — not ideas**. A README may legitimately explain how a feature works and the model can still reason about it. Egress control and the permission ruleset remain separate concerns, and the static ruleset is never altered by content.

#### Configuration

Context Firewall is **enabled by default**. Opt out with:

```sh
export OPENCODE_DISABLE_CONTEXT_FIREWALL=1
```

### Inject environment variables

Inject environment variables into all shell execution (AI tools and user terminals):

```javascript title=".opencode/plugins/inject-env.js"
export const InjectEnvPlugin = async () => {
  return {
    "shell.env": async (input, output) => {
      output.env.MY_API_KEY = "secret"
      output.env.PROJECT_ROOT = input.cwd
    },
  }
}
```

### Custom tools

Plugins can also add custom tools to opencode:

```ts title=".opencode/plugins/custom-tools.ts"
import { type Plugin, tool } from "@opencode-ai/plugin"

export const CustomToolsPlugin: Plugin = async (ctx) => {
  return {
    tool: {
      mytool: tool({
        description: "This is a custom tool",
        args: {
          foo: tool.schema.string(),
        },
        async execute(args, context) {
          const { directory, worktree } = context
          return `Hello ${args.foo} from ${directory} (worktree: ${worktree})`
        },
      }),
    },
  }
}
```

The `tool` helper creates a custom tool that opencode can call. It takes a Zod schema function and returns a tool definition with:

- `description`: What the tool does
- `args`: Zod schema for the tool's arguments
- `execute`: Function that runs when the tool is called

Your custom tools will be available to opencode alongside built-in tools.

:::note
If a plugin tool uses the same name as a built-in tool, the plugin tool takes precedence.
:::

### Logging

Use `client.app.log()` instead of `console.log` for structured logging:

```ts title=".opencode/plugins/my-plugin.ts"
export const MyPlugin = async ({ client }) => {
  await client.app.log({
    body: {
      service: "my-plugin",
      level: "info",
      message: "Plugin initialized",
      extra: { foo: "bar" },
    },
  })
}
```

Levels: `debug`, `info`, `warn`, `error`. See [SDK documentation](https://opencode.ai/docs/sdk) for details.

### Compaction hooks

Customize the context included when a session is compacted:

```ts title=".opencode/plugins/compaction.ts"
import type { Plugin } from "@opencode-ai/plugin"

export const CompactionPlugin: Plugin = async (ctx) => {
  return {
    "experimental.session.compacting": async (input, output) => {
      // Inject additional context into the compaction prompt
      output.context.push(`
## Custom Context

Include any state that should persist across compaction:
- Current task status
- Important decisions made
- Files being actively worked on
`)
    },
  }
}
```

The `experimental.session.compacting` hook fires before the LLM generates a continuation summary. Use it to inject domain-specific context that the default compaction prompt would miss.

You can also replace the compaction prompt entirely by setting `output.prompt`:

```ts title=".opencode/plugins/custom-compaction.ts"
import type { Plugin } from "@opencode-ai/plugin"

export const CustomCompactionPlugin: Plugin = async (ctx) => {
  return {
    "experimental.session.compacting": async (input, output) => {
      // Replace the entire compaction prompt
      output.prompt = `
You are generating a continuation prompt for a multi-agent swarm session.

Summarize:
1. The current task and its status
2. Which files are being modified and by whom
3. Any blockers or dependencies between agents
4. The next steps to complete the work

Format as a structured prompt that a new agent can use to resume work.
`
    },
  }
}
```

When `output.prompt` is set, it completely replaces the default compaction prompt. The `output.context` array is ignored in this case.
