# Workflow resume assumes a part-state field and a boot hook — both are absent

- 2026-09-29, opencode repo
- GOTCHA: two design assumptions are easy to make and BOTH are false in this tree. (a) `WorkflowPart` (packages/schema/src/v1/session.ts:241-248) is `partBase + type/title/steps/plannedBy` — there is NO `state` field; only `ToolPart` has one (packages/schema/src/v1/session.ts:350). `handleWorkflow` never writes the workflow part back either: every `updatePart` in packages/opencode/src/session/prompt.ts:900-1133 creates a NEW assistant/text part. So there is no existing "part-state write path" to reuse for persisting step state or an attempt counter, and adding a `state` field drags in the full schema to protocol to server to SDK codegen chain. (b) There is NO boot hook: `initProjectors()` calls projectors.ts, whose body is `export function initProjectors() {}` — a NO-OP. `runLoop` is reachable only through the `loop` service (packages/opencode/src/session/prompt.ts:2919-2927), driven from httpapi routes. A boot-time re-drive therefore has no host.
- ORDERING CONSEQUENCE: skipping `sweepOrphanedParts` (packages/core/src/session/projector.ts:213, called from :254) for workflow parts WITHOUT first wiring a boot re-drive converts a loud terminal error into a SILENT hang — the part stays `pending` forever and nothing wakes it. Wire the re-drive first, then stop the sweep from consuming workflow parts.
- WHAT DID WORK for the durable counter: a new core table created with `bun run script/migration.ts` from `packages/core` (NOT `bun drizzle-kit generate`), landed as commit `972dda93a9` (`workflow_attempt`, replacing a process-local Map that reset the re-dispatch cap on every restart).
- STATUS: post-crash resume remains an UNDESIGNED slice — root AGENTS.md states "post-crash retry needs explicit design"; specs/v2/session.md:104 and specs/v2/todo.md:62 list it as an explicit slice to design.
- ACCEPTANCE GATE: before proposing any workflow-resume change, assert (a) the durable field or table it will persist to exists, and (b) a boot or wake path exists that can re-drive the V1 loop. If either is absent, that is a DESIGN task, not a wiring fix.
